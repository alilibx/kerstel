# Automatic pulls Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every synced device pulls on its own every five minutes, through a launchd agent or a systemd user timer, so `ks sync` is needed only to settle a conflict (#105).

**Architecture:** A new module, `packages/cli/src/sync/timer.ts`, renders and installs a per-home timer that runs `kerstel sync --background --timer`. `setup`, `join`, and a foreground `ks sync` install or refresh it. A background sync installs it when it's missing, which covers devices that synced on 0.3.0, and leaves a one-line notice for the next command. `sync off` and `uninstall` remove it. `run` and `exec` now start a sync when none has finished in the last minute, or in the last five after a failure.

**Tech Stack:** TypeScript on Bun 1.4.2, `bun:test`, `bun:sqlite`; `launchctl` on macOS, `systemctl --user` on Linux. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-13-easy-sync-design.md` §8 (on `main` once PR #115 merges), and sync spec `docs/superpowers/specs/2026-11-08-sync-between-devices-design.md` §8.1, which this PR updates.

## Global Constraints

- The daemon gains no network code. Pulls run in the separate `kerstel sync --background` process (sync spec §8.1).
- The interval is five minutes: `StartInterval` 300 on launchd, `OnUnitActiveSec=5min` on systemd.
- `run` and `exec` never wait on the network and never fail because the server is unreachable.
- A unit file never records a secret. Its environment holds only `KERSTEL_HOME` (absolute), `KERSTEL_KEYCHAIN_BACKEND`, `KERSTEL_KEYCHAIN_SERVICE`, the network settings `backgroundSyncEnv` already passes (`NETWORK_SETTINGS`), and `KERSTEL_DAEMON_SCRUBBED=1`.
- Kerstel never enables systemd lingering and never unlocks a keyring.
- Tests never touch the real `~/Library/LaunchAgents`, `~/.config/systemd/user`, `launchctl` or `systemctl`. Tests must never print a secret, and they clean up every temporary home.
- `ks sync` is never described as a step to run regularly. The conflict line (sync spec §8.4) is the only place that tells you to run it.
- Copy uses `cliName()` for the command name, and status lines go to stderr with `process.stderr.write`, not `console.error`, which Bun paints red on a TTY.
- Every user-visible change gets a line in `CHANGELOG.md`'s unreleased section, and the website and README copy match the CLI source (AGENTS.md).

## Review Focus

1. **A binary path or `KERSTEL_HOME` with spaces, quotes or `&`.** The plist must be valid XML and the systemd `ExecStart=` and `Environment=` lines must round-trip. Tests: Task 1, `renders a path with spaces and XML specials`.
2. **Two Kerstel homes on one machine** (a custom `KERSTEL_HOME`, or a test home). Each gets its own timer, and removing one leaves the other. Tests: Task 1, `names differ per home`; Task 2, `remove leaves another home's timer`.
3. **The binary moved or the shell's settings changed after install.** `status()` reports `current: false`, a foreground `ks sync` rewrites the unit, and `doctor` warns. Tests: Task 2, `status is not current when argv differs`; Task 5, the doctor warning.
4. **The timer fires after sync was turned off**, for example when `sync off` couldn't remove the unit. The timer-started sync removes its own timer and exits 0. Test: Task 3, `a timer run with sync off removes the timer`.
5. **A watch loop that starts `kerstel run` every few seconds** spawns at most one sync a minute, and an unreachable server spawns at most one every five minutes. Tests: Task 4.

### Task 2: Install, check and remove the timer

**Files:**
- Modify: `packages/cli/src/sync/timer.ts`
- Modify: `packages/cli/scripts/test-tmpdir.ts` (the test preload)
- Test: `packages/cli/test/sync-timer.test.ts`

**Interfaces:**
- Consumes: Task 1's renderers and `timerName`; `cliCommand` from `daemon/spawn.ts`; `kerstelHome` from `paths.ts`.
- Produces:
  - `type TimerStatus = { state: "installed"; kind: "launchd" | "systemd"; current: boolean } | { state: "missing"; kind: "launchd" | "systemd" } | { state: "unavailable"; reason: string }`
  - `type EnsureResult = "installed" | "updated" | "unchanged" | "unavailable"`
  - `interface TimerDeps { platform: NodeJS.Platform; userHome: string; home: string; defaultHome: string; env: NodeJS.ProcessEnv; argv: string[]; uid: number; run: (argv: string[]) => { code: number; stdout: string } }`
  - `interface SyncTimer { status(): TimerStatus; ensure(o: { rewrite: boolean }): EnsureResult; remove(): boolean }`
  - `syncTimer(deps?: Partial<TimerDeps>): SyncTimer`. The defaults use the real platform, `os.homedir()`, `kerstelHome()`, `process.env`, `cliCommand(["sync", "--background", "--timer"])`, `process.getuid()` and `Bun.spawnSync`. When `process.env.KERSTEL_TEST_NO_SYNC_TIMER === "1"` and no `run` dep is given, it returns a timer whose `status()` is `{ state: "unavailable", reason: "disabled in tests" }` and whose other methods do nothing.

Behaviour to implement:
- **launchd (darwin):** the file is `<userHome>/Library/LaunchAgents/<label>.plist`, mode `0644`. Installing runs `launchctl bootout gui/<uid>/<label>` (ignoring failure), then `launchctl bootstrap gui/<uid> <file>`. Removing runs the `bootout` and deletes the file.
- **systemd (linux):** files go in `${XDG_CONFIG_HOME:-<userHome>/.config}/systemd/user/<name>.{service,timer}`. The timer is available only when `systemctl --user show-environment` exits 0; otherwise it reports `unavailable` with the reason `no systemd user session`. Installing runs `systemctl --user daemon-reload`, then `systemctl --user enable --now <name>.timer`. Removing runs `disable --now`, deletes both files, and runs `daemon-reload`.
- **Any other platform** reports `unavailable` with the reason `not supported on <platform>`.
- `status().current` is true when the files on disk equal what the renderers produce now, from `deps.argv` and `timerEnv(deps.env)`.
- `ensure({ rewrite: false })` installs only when the timer is missing. `ensure({ rewrite: true })` also rewrites and reloads when it isn't current. A failed `launchctl` or `systemctl` call returns `"unavailable"`. It never throws.

- [ ] **Step 1: Write the failing tests.** They use a temp `userHome` and a fake `run` that records argv and returns scripted exit codes:
  - `installs a launch agent`: on platform `darwin`, `ensure({rewrite:false})` returns `"installed"`, the plist exists with mode `0644`, the calls include `["launchctl","bootstrap","gui/501",<file>]`, and `status()` returns `{state:"installed",kind:"launchd",current:true}`.
  - `installs a systemd user timer`: on `linux`, the calls include `systemctl --user daemon-reload` and `systemctl --user enable --now kerstel-sync.timer`, and both files exist.
  - `no systemd user session`: when `show-environment` exits 1, `status()` is `unavailable` with the reason `no systemd user session`, `ensure` returns `"unavailable"`, and no file is written.
  - `status is not current when argv differs`: install with one argv, then `syncTimer` with another argv. `status().current` is false. `ensure({rewrite:false})` returns `"unchanged"` and leaves the file as it was. `ensure({rewrite:true})` returns `"updated"` and the file now holds the new argv.
  - `remove leaves another home's timer`: install for home A and home B under one `userHome`, remove A, and B's file still exists.
  - `test runs never install`: `syncTimer()` with no deps, under the preload, reports `unavailable` and writes nothing under the real `os.homedir()`.
- [ ] **Step 2: Run** `bun test packages/cli/test/sync-timer.test.ts`. Expected: the new tests FAIL.
- [ ] **Step 3: Implement** `syncTimer` and the platform branches in `timer.ts`, and set `process.env.KERSTEL_TEST_NO_SYNC_TIMER = "1"` in `scripts/test-tmpdir.ts`.
- [ ] **Step 4: Run** the file, then the whole suite with `bun run test`. Expected: PASS, and `~/Library/LaunchAgents` holds no new `dev.kerstel.sync*` file (check with `ls`).

### Task 3: Use the timer in `ks sync`

**Files:**
- Modify: `packages/cli/src/commands/sync.ts` (`SyncDeps`, `setup`, `join`, `run`, `background`, `off`, `status`, `USAGE` unchanged)
- Modify: `packages/cli/src/sync/state.ts` (`SYNC_META`)
- Modify: `packages/cli/src/sync/background.ts` (`SyncGlance`, `glanceSync`, notice helpers)
- Modify: `packages/cli/src/index.ts` (print the notice)
- Test: `packages/cli/test/sync.test.ts`

**Interfaces:**
- Consumes: `SyncTimer`, `syncTimer`, `TimerStatus` from Task 2.
- Produces:
  - `SyncDeps.timer?: SyncTimer`
  - `SYNC_META.lastTimer = "sync_last_timer"` holds the ms timestamp of the last timer-started sync. `SYNC_META.timerNoted = "sync_timer_noted"` is set once the "can't schedule" notice has been left.
  - `SyncGlance.lastTimer: number | null`
  - `syncNoticePath(home?: string): string`, which is `<kerstelHome>/sync-notice`.
  - `leaveSyncNotice(line: string, home?: string): void` and `takeSyncNotice(home?: string): string | null`. Taking a notice reads the file and deletes it, and never throws.

Behaviour to implement:
- **`setup` and `join`,** after they succeed, call `timer.ensure({ rewrite: true })`. If it's scheduled: `ok("Pulls changes every five minutes on its own.")`. If it's `unavailable`: `info(\`Can't schedule pulls here (${reason}). Kerstel still pulls when you run, exec, or change a secret.\`)`.
- **A foreground `ks sync`** calls `ensure({ rewrite: true })` after the sync. On `"updated"` it prints `dim("Updated the scheduled pull to match this shell's settings.")`. It prints nothing otherwise.
- **`background`** accepts an optional `--timer` argument; any other argument still returns 2. With `--timer` it writes `SYNC_META.lastTimer` when it starts. If sync is off (no `vaultId`) and `--timer` was given, it calls `timer.remove()` and returns 0. After a successful sync it calls `ensure({ rewrite: false })`:
  - On `"installed"` it leaves the notice `` `kerstel: sync now pulls changes every five minutes on its own. Run \`${cliName()} sync off\` to stop syncing this device.` ``
  - On `"unavailable"`, if `timerNoted` isn't set, it sets it and leaves `` `kerstel: can't schedule sync pulls here (${reason}). Kerstel still pulls when you run, exec, or change a secret.` ``
- **`off`** calls `timer.remove()` in both of its success branches, including "no longer in the vault".
- **`status`** gains one line after `Last sync`: `` Pulls        every 5 minutes (launchd), last ran <when(lastTimer)> ``. When the timer is missing it shows `` not scheduled: run `${cliName()} sync` to add it `` in yellow. When it is unavailable it shows `` not scheduled (<reason>) `` dimmed.
- **`index.ts`,** in the non-background branch before `syncBeforeCommand`, calls `takeSyncNotice()` and writes any line to stderr, dimmed, with `process.stderr.write`.

- [ ] **Step 1: Write the failing tests** in `sync.test.ts`, using the existing in-process server helpers and a fake `SyncTimer` that records calls and returns scripted results:
  - `setup schedules pulls`: `ensure` is called with `{rewrite:true}` and the output includes `Pulls changes every five minutes on its own.`
  - `setup says when it can't schedule`: with `ensure` returning `"unavailable"` and status reason `no systemd user session`, the output includes `Can't schedule pulls here (no systemd user session).`
  - `join schedules pulls`: as in the setup test, on the joining device.
  - `a 0.3.0 device gets the timer on its next background sync`: on a synced vault where `ensure` returns `"installed"`, `syncCommand(["--background"])` returns 0 and `takeSyncNotice()` returns the "now pulls" line. A second `takeSyncNotice()` returns null.
  - `the can't-schedule notice is left once`: two background syncs with `ensure` returning `"unavailable"` leave the notice only once.
  - `a timer run with sync off removes the timer`: on a vault without sync, `syncCommand(["--background","--timer"])` returns 0 and calls `remove()` once. Without `--timer` it does not call `remove()`.
  - `a timer run records when it ran`: after `--background --timer`, `glanceSync().lastTimer` is a number within the test's clock window.
  - `background refuses unknown arguments`: `["--background","--nope"]` returns 2.
  - `sync off removes the timer`: `remove()` is called once.
  - `status shows the schedule`: for each of installed, missing and unavailable, the `Pulls` line matches the copy above.
- [ ] **Step 2: Run** `bun test packages/cli/test/sync.test.ts`. Expected: the new tests FAIL.

### Task 4: `run` and `exec` sync more often

**Files:**
- Modify: `packages/cli/src/sync/background.ts` (`BACKGROUND_PULL_AFTER_MS`, `syncBeforeCommand`)
- Modify: `packages/cli/src/sync/state.ts` (the `lastTry` doc comment)
- Test: `packages/cli/test/sync.test.ts`

**Interfaces:**
- Produces: `BACKGROUND_PULL_AFTER_MS = 60_000` and `BACKGROUND_RETRY_AFTER_MS = 5 * 60_000`. `syncBeforeCommand` keeps its signature.

Rule: when `lastError !== null` (the latest sync failed), start one only if `now - lastTry >= BACKGROUND_RETRY_AFTER_MS`. Otherwise start one if `now - max(lastOk, lastTry) >= BACKGROUND_PULL_AFTER_MS`. Syncs that start during one another's run are already absorbed by the lock: the later one exits without a request, through the "finished after it started and left nothing to push" check.

- [ ] **Step 1: Update and add the tests** around the existing `syncBeforeCommand` tests:
  - `run syncs a minute after the last success`: `lastOk = now - 59_000` gives false, and `now - 60_000` gives true.
  - `run backs off five minutes after a failure`: `lastOk = now - 10 min`, `lastTry = now - 4 min` and `lastError = "x"` give false. At `lastTry = now - 5 min` it gives true.
  - `a watch loop spawns at most one sync a minute`: simulate 30 calls 2 s apart with a glance that records the spawn as `lastTry`. It spawns exactly once.
  - Any existing test that asserts five minutes after a success is changed to one minute.

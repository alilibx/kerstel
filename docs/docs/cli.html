CLI reference

Every command that names a secret takes a reference in the form <scope>/<KEY>, where scope is global or a project name.

ks works everywhere kerstel does — it's a shortcut for the same binary, installed by install.sh alongside kerstel. Every command below works under either name.

Setting up a project

Command What it does
kerstel init [--yes] [--dry-run] Show every .env variable grouped by where it suggests putting it, then walk through "Look right?" (accept every suggestion, change some from a checklist, or go through them one by one), an optional .gitignore question, and "Apply these changes?" (apply, show the full diff first, or cancel). Once applied: store each value in the vault, rewrite the files with references, and wire the runtime hook into your scripts through a launcher it writes at .kerstel/exec.cjs: every command becomes node .kerstel/exec.cjs -- <command>. Commit the launcher with package.json. On your machine it runs kerstel exec; on a deploy host with no Kerstel it prints one line and runs the command unchanged, so npm run build works everywhere (see Deploying). A re-run rewrites a launcher that is out of date or edited, converts scripts wired by an older Kerstel (kerstel exec -- ...), and warns when .gitignore hides .kerstel/. A script made of several commands (node copy.mjs && next dev) is wired one command at a time, with the wrapper placed after any leading NAME=value words, so NODE_ENV=production next start becomes NODE_ENV=production node .kerstel/exec.cjs -- next start; a re-run finishes a script wired only in part. Commands that never run JavaScript (rm, echo, mkdir, and the like) are left alone. A script is skipped, with the reason named, when it changes directory (cd), uses shell control (subshells, backticks, if, export), redirects (>, <, &), has an unbalanced quote, or has no command to wire. Each folder is registered on its own, so a second checkout of the same package (a git worktree) keeps the first one's registration and reuses its secrets. A value the vault already holds for this project becomes a reference without being stored again; when it differs, init asks which one stays (the vault's, by default, and under --yes). A value the shared vault holds is reused only when it is the same; a different shared value is left alone and the key stays with this project, unless you choose the shared vault with --global or in Look right?, which asks which one stays. If the derived scope already belongs to a different package, init stops and names it; re-run with --scope <name>, or pass that package's scope with --scope to share it on purpose. A re-run in a registered folder keeps the scope it was registered under. Run it from the project root; it needs a readable package.json. At a monorepo root (a package.json with workspaces, or a pnpm-workspace.yaml), it first lists every package with .env files and asks which to set up (all of them under --yes), then shows one overview with a section per package, asks Look right? once (the checklist names keys as apps/web: DATABASE_URL), asks one .gitignore question for the root's and each package's own, and applies package by package, stopping at the first that fails and naming it; the ones before it stay set up. A key two or more packages hold with the same value is suggested for the shared vault. There --scope renames the root package only; run init --scope <name> inside a package to rename that one.
kerstel move [KEY...] [--to global|project|plaintext] [--yes] [--replace] [--allow-tracked] Change where a key lives after init: this project's vault, the vault shared by all your projects, or plain text in the env file. With no arguments it lists every key and where it lives now, asks which to move and where, previews the change with values shown only as their length, and asks Apply? (default No). With key names and --to it asks nothing but Apply?, and --yes answers that. Every env file that defines the key is rewritten, after an encrypted backup; if one changed since it was read, it refuses and changes nothing. A project copy that neither this checkout nor any other registered checkout of the project still reads is removed from the vault and saved in the backup; a shared (global) copy is never removed. If the destination already holds a different value it asks which one stays; the direct form refuses unless --replace. Writing a value into a file git tracks or does not ignore warns, and the direct form refuses unless --allow-tracked. A key whose reference the vault does not hold is named and skipped, not offered (kerstel init stores it first). Moving to plain text, a value with no plain-text spelling that fits a covered line's own quoting is left in the vault and named, rather than written in a form that would change it. Without a terminal it needs key names, --to and --yes.
kerstel exec -- <command> Run one command with the runtime hook wired in. It resolves nothing itself: it sets KERSTEL_SOCKET, KERSTEL_TOKEN_FILE (the path of the session token file, never the token) and KERSTEL_HOOK_DIR, appends --require <the hook> to NODE_OPTIONS, and adds --preload=<the hook> for a bun or bunx command, which NODE_OPTIONS does not reach. The launcher init writes into your scripts calls it when Kerstel is on PATH, never from node_modules/.bin. If the command is not on PATH (or, given as a path, does not exist), it says so before opening the vault or starting the daemon and, in a project, names the install command for your package manager (bun install, npm install, pnpm install, or yarn install), then exits 127 as a shell would.

kerstel init flags

Flag What it does
--dry-run Prints the plan and every diff, then stops before the first write. Diffs mask every value, the text of every comment in an env file, and the values a package.json script sets inline (NAME=value, a --token-style flag, a URL's password). Nothing reaches your project, your vault, or ~/.kerstel.
--yes Takes every suggestion and every default, asking nothing.
--scope <name> Use this scope instead of the one derived from your package.json name. Lowercase letters, digits, ., _ and -.
--global KEY[,KEY] Put those keys in the global scope without asking.
--keep KEY[,KEY] Leave those keys as plaintext without asking.
--non-interactive Never asks. Applies the suggested plan like --yes, and on any question no flag can answer — a value this machine is missing, for instance — exits 2 naming the flag that would have supplied it.
--from-stdin Reads {"KEY": "value"} JSON from stdin for references whose values this vault does not have yet. Pair it with --non-interactive in a script. At a monorepo root a value may be nested by package path, {"apps/web": {"KEY": "value"}} ("." for the root); a flat one applies to every package that lacks it.

When the same key appears in several files, the highest-precedence one is stored: .env.<x>.local, then .env.local, then .env.<x>, then .env. Every occurrence points at that single reference.

Finding secrets

Command What it does
kerstel scan [path] [--keys] [--all] [--json] [--verbose] Find every env file under a folder (the current one by default; kerstel scan ~ covers your home folder) and report what each one holds, without printing a value or changing anything. It reads env files (.env, .env.local, .env.production, ...), backup copies (.env.bak, .env~, swap files, which are listed but not read), and templates (.env.example, .env.sample, ...). Each line is a reference (any of the three forms, checked against this vault by name, so there's no Keychain prompt and no ~/.kerstel is created), a secret (what init would store because of the key's name, a URL with a password or a token in it, a known token prefix like sk_live_ under any name, or a private key), unclear (init would store it only because it can't tell), or config. In a template only a real-looking token, URL password, query token or private key counts; sk_test_xxx and postgres:postgres@localhost are placeholders. Inside a git repository it says whether a file with secrets is tracked by git (flagged first, with the advice to rotate the keys, since they stay in history) or not ignored. Files are grouped by project (the nearest folder with a package.json) and monorepo, and the summary says what to do with each: run kerstel init in a project, delete a backup, or store the value of a nested env file init doesn't read with kerstel set. It never enters node_modules, .git, package manager caches, ~/.kerstel, or ~/Library on macOS, never follows a symlinked folder, and stays on one disk. On macOS, scanning ~ reads Desktop, Documents and Downloads, so the system may ask once whether your terminal can access them; folders you don't allow are counted as unreadable. Exits 1 when any secret is in plain text, 0 otherwise, and 2 for a folder that doesn't exist; unclear lines and unresolved references don't change the exit code, so it can run in CI or a cron job.
Flag What it does
--keys Name each finding's key and line number under its file. Values are never shown.
--all List projects with nothing to do too. By default they're counted in one line.
--json Print one JSON object, described below, instead of the report. It always includes key names and line numbers.
--verbose List the folders that could not be read.

--json prints { root, folders, unreadable, git, projects }. git is false when git isn't installed. Each project has path, name, workspace (its monorepo root, or null), packageJson, scope (the scope it's set up under, or null), and files. Each file has name (relative to the project, such as docker/.env), kind (env, template, or backup), read, git (tracked, not-ignored, ignored, or null outside a repository), secrets and unclear (lists of { key, line }), config (a count), references (lists of { key, line, ref, inVault }, with ref always in the full ks:<scope>/<KEY> form), and unreadableLines (line numbers). A change to this shape is a breaking change.

Secrets

Command What it does
kerstel set <scope>/<KEY> [--value <value>] Store or overwrite a secret. Without --value, the value must be piped on stdin; a terminal with nothing piped in fails rather than waiting.
kerstel get <scope>/<KEY> [--reveal] Read a secret. Prints a masked value unless --reveal is given.
kerstel ls [--scope <scope>] List stored references, optionally for one scope. Values are never listed.
kerstel ui Browse and manage the vault full screen in the terminal. The Secrets screen lists every stored secret, global first and then each project scope, with its value masked and the time it last changed. On it, r reveals the value on the current row until your next key, writing a reveal audit row first; a adds a secret (pick global, an existing scope, or a new one, type the key, then the value, which echoes only dots, and confirm); e replaces the value on the current row; and d deletes it, after saying how many project files reference it. Scopes, keys and values are checked as kerstel set checks them, with the same messages, and an add that names an existing secret asks before replacing it. The References screen is kerstel refs as a tree, with b to group by key, R to scan again, and Enter to jump from a reference to its secret. The Audit screen is kerstel audit as a list, newest first, 200 rows at a time, with reveals marked. Its summary covers the last 7 days, and its rows go back through everything kept: a shows one action or all of them, n loads 200 more, and Enter jumps to the secret on that row if it still exists. Tab or 1 2 3 switch screens, j k or the arrows move, / filters, ? lists every key, and q or Ctrl-C quits. It opens the vault the way kerstel set does, talks to no daemon, and listens on nothing; the terminal is restored however it exits, and nothing it shows stays in your scrollback. It needs an interactive terminal of at least 60×16; in a pipe, use kerstel ls and kerstel refs.
kerstel audit [--scope <s>] [--key <KEY>] [--action <a>] [--since <7d|24h|date>] [--limit <n>] Show what Kerstel did with your secrets on this device. It opens with a summary, then lists Reveals (every time a person asked to see a value, each with a hint to rotate the credential when it is still the value that was shown), App reads (grouped by project and process), and Changes (set, remove, sync and device rows). It never prints a value. It covers the last 7 days and shows 50 rows per section; --since takes days (7d), hours (24h) or a date (2026-11-01), --limit raises the row count (a section it cuts short says so), and --scope, --key and --action narrow the list. Actions are resolve, run, reveal, set, remove, sync and device; with resolve or run, App reads lists each row instead of grouping. Each row carries the chain of programs that started the command or app (names only, which a program that wants to hide can fake) and the project checkout. Rows stay on this device and never sync, and the daemon deletes rows older than 90 days.
kerstel refs [--by-key] Show which project files reference which secrets, across every folder init set up: grouped by scope, then folder, then env file, with each reference in the ks:<scope>/<KEY> form. A reference the vault doesn't hold is marked ✗ not in the vault. Then come the set-up folders it can't read (gone, or without a readable package.json), env files it can't read, and the secrets no readable project references. A secret on that last list is not used by any file refs could read; when a folder or file above it couldn't be read, the heading says so, and you should check those before deleting anything. A vault it can't read is an error, not an empty list. --by-key turns it around: each secret, then the files that reference it, which tells you what a rotation or rm touches. It reads only key names from the vault, never values, so it needs no Keychain access and works before any vault exists. It never changes a file. It exits 0 whatever it finds, since kerstel doctor is the command that judges, and 1 only when the vault itself can't be read.
kerstel rm <scope>/<KEY> --yes Remove a secret. --yes is required; there is no interactive confirmation.

Running code

Command What it does
kerstel run -- <command> Resolve every reference in the current environment, then run the command with real values injected. Works for anything that cannot load the runtime hook. A command that is not on PATH gets the same message and exit 127 as with exec.
kerstel exec -- <command> Run the command with the hook wired in and the references left untouched, so each one resolves lazily on the read (under Bun, also once at startup, so Bun.env sees the value). See above.
kerstel resolve ks:<scope>/<KEY> Print one resolved value. Useful in scripts. The key is required here: there is no variable to take it from. It is recorded as a reveal, not a resolve, because a person asked to see the value.

Sync

End-to-end encrypted sync of the vault between your own devices, through a kerstel-server you run. The server stores ciphertext only: it never holds a key that opens a value, a key name, or a device name. Set it up on one device, then pair each other device with add-device on a device already in the vault and join on the new one. The Sync guide walks through it, including running the server.

Once sync is on, it runs in the background too. After set, rm, init, move or ui leave changes to push, Kerstel starts a detached kerstel sync --background. run and exec start one when none has started in the last minute, or five minutes after a failed one. Neither waits for the network or fails because of it; the result is in sync status and doctor. One lock file, ~/.kerstel/sync.lock, keeps two syncs on one device from running at once: a sync you start waits up to 30 seconds for a background one to finish, and a background one waits its turn. Pairing can take longer than a background sync waits, so add-device and join start one when they finish if changes made meanwhile wait to be pushed. The operating system releases the lock when a sync's process ends, however it ends. Every five minutes a launchd agent (dev.kerstel.sync, macOS) or a systemd user timer (kerstel-sync, Linux), each with a short suffix for a custom KERSTEL_HOME, also runs kerstel sync --background --timer, installed by sync setup and sync join, and added by the next sync on a device that lacks it, and updated by the next kerstel sync you run when its settings changed. The unit records only KERSTEL_HOME (always, as the full path of the home it pulls for), the credential-store settings, proxy and CA settings, and KERSTEL_DAEMON_SCRUBBED, never a secret, and only you can read it. It clears BUN_OPTIONS, NODE_OPTIONS and each credential-store setting your shell leaves unset, so nothing set for your whole login session reaches it. It pulls while you are logged in. A run that finds no vault, as when KERSTEL_HOME is on a drive that isn't mounted yet, does nothing and keeps the timer; sync off and uninstall remove it. Where it can't be scheduled (no systemd user session on Linux, or no GUI login session on a Mac nobody is logged in to, as over SSH), every kerstel sync you run says so. A background sync never chooses between two values: while a conflict is open, every command except sync prints one line on stderr, kerstel: 1 sync conflict. Run `kerstel sync` to choose which value stays.

Command What it does
kerstel sync setup <url> [--pin <pin>] [--yes] Turn sync on for this vault and upload every secret. The URL must be https://, or http:// to this machine. --pin sha256/… pins the certificate of a server that runs kerstel-server --tls self, which prints the pin when it starts; it needs an https:// URL. The pin travels in the add-device line, so other devices never type it, and every request checks the server's key: if it changes, nothing is sent. Without --pin, such a server's certificate can't be checked, and setup says to pass the pin. It shows the server, the pin when there is one, how many secrets and scopes it will upload, and this device's name (sealed, so the server never sees it), then asks before uploading; without a terminal it needs --yes. A server that needs an enroll token reads it from KERSTEL_SYNC_ENROLL_TOKEN.
kerstel sync [--keep local|remote] [--reveal] Pull what your other devices changed, then push what changed here. A value a pull replaces or deletes is saved first in an encrypted backup under ~/.kerstel/backups/_sync/. A key changed both here and on another device is a conflict: this device keeps its value and stops pushing that key until you choose. In a terminal kerstel sync asks for each one, showing each side only as its length (--reveal shows both values); --keep local or --keep remote settles them all, and the value that loses goes to the backup. Without a terminal or --keep, it lists the conflicts by name and exits 1.
kerstel sync status The server, a Certificate line when the server is pinned, the last successful sync, how many changes wait to be pushed, open conflicts, the last error, including a background sync's, and a Pulls line: every 5 minutes (launchd) or (systemd) with when it last ran, not scheduled yet: added on the next sync, or not scheduled (<reason>). Works offline.
kerstel sync devices Every device in the vault: its name and platform (opened here), its key fingerprint, when it was added, and when it last synced. A device whose listed keys don't match the ones sealed with its name is marked unverified: no device in the vault added it with those keys. After another device replaces the sync key, names show as sealed with a newer key until this device runs kerstel sync.
kerstel sync add-device Pair another device. It shows one kerstel sync join ks1-… line to run on the new device, and copies it to the clipboard when it can; the value works once and expires in 10 minutes, so treat it as a secret until then. It also prints a hint to update a device running an older Kerstel first. When the new device answers, it shows that device's name, platform and key fingerprint (the new device shows the same fingerprint, so you can compare them) and asks whether to add it, defaulting to No. There is no --yes for this question, so it needs a terminal. On no, or when the value expires, nothing is added.
kerstel sync join [<value>] Join a synced vault from a new device, with the line add-device showed. Pass the value as an argument, or run it with no arguments and paste it at a hidden prompt. kerstel sync join <url> <code> still works, for pairing from a device on 0.3. A value from a newer Kerstel, or one that is cut short, is refused with a hint. It names the server it joins, then waits until you confirm on the other device, then checks that the sync key it receives is the one that device confirmed: if the server swapped in a key of its own, it refuses and saves nothing. It then pulls the vault and merges this vault's own secrets into it: a key only this device holds is uploaded, one both hold with the same value is left alone, and one they hold with different values is a conflict, settled as with kerstel sync.
kerstel sync remove-device <name> Remove another device, named as sync devices lists it (or by its key fingerprint, when two share a name). It replaces the sync key: every record is encrypted again under a new key that only the remaining devices receive, and the removed device's requests are refused from then on. If another device pushes meanwhile, it pulls and starts again, so that change is kept. It refuses while a conflict is open, and stops without changing anything if a device the server lists is unverified, so the new key never goes to a key the server swapped in. The removed device already had every value, so it reminds you to rotate any secret it should no longer hold. To remove this device, use sync off.
kerstel sync off [--delete-vault] Stop syncing this device and remove its scheduled pull: it leaves the vault on the server, and its secrets stay here. On the vault's last device it refuses unless --delete-vault, which deletes the vault from the server too. A device that another one already removed just turns sync off, and so does a device whose pinned server now answers with a different key, or whose sync settings can't be read, since it can no longer leave the vault there.

Daemon and diagnostics

Command What it does
kerstel daemon start Start the resolver daemon in the background.
kerstel daemon stop Stop it.
kerstel daemon status Report whether it is running and where its socket is.
kerstel daemon serve Run the daemon in the foreground. Used by start; handy for debugging.
kerstel doctor [--verbose] Diagnose this machine, grouped under This machine (version, vault, daemon, runtime hook, file permissions, a warning when BUN_OPTIONS is set since Kerstel's own process honours it, whether ks resolves to this binary, and Sync: off, or the server, the last successful sync, changes waiting to be pushed and open conflicts, and pulls every 5 minutes, last ran …, with a warning for an open conflict, a failed last sync, seven days without a successful one, a missing scheduled pull (Fix: kerstel sync, to schedule them) or one whose settings differ from this shell's (Fix: kerstel sync, to update it); a machine that can't schedule pulls shows that as information only; an idle daemon is shown as information, since it starts on its own when a script needs a secret; the version row is a warning with Fix: kerstel update when a newer release exists, and information when the release page could not be reached) and, inside a project with a package.json, This project, headed with the scope this folder is registered under, or the one init would derive for it (how many of the wrappable scripts are wired through kerstel exec, naming any that are only partly wired, any still in the old kerstel exec form, and any init skips with the reason; whether .kerstel/exec.cjs is current, with a problem when it is missing and a warning when it is out of date, edited, or not Kerstel's; a problem when node_modules/.bin here or in a parent directory holds a kerstel or ks that would run in place of Kerstel, how many references in your .env* files this vault can resolve, any env file it could not read, and, as information, the other registered checkouts of the same package under that scope: Also checked out at <folder>). Every warning or problem prints a Fix: line naming the command that resolves it. --verbose adds the paths and permission modes behind each check: home, vault, token, socket, and hook. Exits 1 if any check reports a problem, 0 otherwise — warnings alone still exit 0.
kerstel update [--check] Install the latest release over this binary. It reads the newest version from GitHub Releases, downloads the binary for this platform and the release's SHA256SUMS, verifies the checksum, runs the new binary once to confirm it reports that version, and only then swaps it into place. ks keeps working, since it links to the same file. If a resolver daemon is running it is stopped, so the next resolution starts the new version. On a terminal it draws a progress bar while the binary downloads and names each step; piped, it prints plain lines. It says so and exits 0 when you already have the latest release, and exits 1 when GitHub cannot be reached; a failed checksum or download installs nothing. --check only reports whether a newer release exists. Run from source there is no binary to replace, so update refuses; --check still works.
kerstel --version Print the version, such as 0.1.0. On a terminal it also checks GitHub and adds a second line on stderr: Up to date., 0.1.1 is available. Run kerstel update., or Could not check for updates. Piped or redirected, it prints only the version and never touches the network.
kerstel uninstall Remove Kerstel from this machine. For every project init set up, and every checkout of it, it rewrites each reference (ks: or kerstel://) back to the value in the vault, in the quoting the line had before init (falling back to a quoting that can hold the value only when that one cannot), unwraps the package.json scripts (both the launcher form and the older kerstel exec form), deletes .kerstel/exec.cjs when it is Kerstel's (a file without Kerstel's marker line is left alone and named), and turns the .gitignore note back into .env and .env.* lines. It opens the vault without creating anything, so on a machine with no vault it says so and removes only the binary and any vault key left orphaned in the credential store. Otherwise it shows every diff with values masked (comments in env files, and values a package.json script sets inline, are masked too) and asks once, defaulting to No, keep Kerstel; before writing anything it checks that every planned file is writable, and if one is not, names it and changes nothing. Once every file is written, a synced device leaves its vault on the server (on the vault's last device, the question asks whether to delete the vault from the server too, defaulting to no, and --yes never deletes it; if the server can't be reached, it says to remove this device from another one with sync remove-device and carries on). Then it removes the scheduled sync pull (the plan says Removes the scheduled sync pull. when one is installed), after waiting up to 30 seconds for a running sync to finish, stops the daemon, waits for it to finish exiting, and deletes ~/.kerstel (if something still holds files open there, it says so and exits 1), the vault key, the binary, and every kerstel or ks link that points at that binary, in the binary's folder, the folder it was run from, and each folder on PATH — the binary and links only when running the compiled kerstel, not from source. A ks that is a real file or points elsewhere is left alone. It refuses, naming each one, if a project cannot be reached (its folder is gone, it has no package.json, or its package.json is not valid JSON), a reference cannot be resolved, a secret is used by no project, or a value exists only in an encrypted backup: a key that had different values in several .env files, or twice in one, which init stored once, found in any of its backups; or a value move or init saved in its backup (one it removed or replaced in the vault, or a plain value that lost to the vault's, as when init keeps the vault's value over a differing one in the file) that is now neither in the vault nor in a restored file. A backup it cannot decrypt counts too, since it may hold such a value. Save the secrets with get --reveal, recover any backup-only value from where it came from, then pass --force. Afterwards it warns that the .env files hold plaintext again, and names each one git already tracks, with the git rm --cached command to untrack it. With a custom KERSTEL_HOME on the macOS Keychain or Secret Service, it leaves the vault key in place, since every home on the machine shares that one key. If the credential store keeps the vault key (for example, you deny the Keychain prompt), it says so, leaves the binary, and exits 1; run it again to delete the key. --dry-run prints the plan and changes nothing; --yes skips the question but never implies --force.
kerstel (no command) or kerstel --help List every command with a one-line description. Bare kerstel (or ks) also shows the banner; --help prints the same list without it. Both exit 0.

Environment variables

Variable Effect
KERSTEL_HOME Directory for the vault, socket, and hook assets. Defaults to ~/.kerstel.
KERSTEL_KEYCHAIN_BACKEND Force a credential store backend. Set to file for a 0600 key file instead of the OS store. When Kerstel falls back to the file on its own, because no credential store answered, every command that opens the vault warns on stderr; setting this to file says you meant it, and turns the warning off.
KERSTEL_RELEASES_URL Where update, doctor, and --version look for releases, instead of https://github.com/alilibx/kerstel. For mirrors and tests; it must serve the same /releases/latest redirect and /releases/download/v<version>/ files as GitHub. It must be https:// (or http:// to 127.0.0.1 or localhost); anything else is refused, and doctor names it. update prints the mirror it uses.

Set these in your shell or your shell profile, never in a project's env file. Kerstel is a Bun binary, so it loads the .env of the directory you run it in — and in Kerstel's model that file is committed, which would let a repository you cloned choose your vault's location or your credential store. So if an env file here names a KERSTEL_* variable, Kerstel ignores that variable and says so on stderr.

The test is the name, not the value, and that matters in one case: a variable you set yourself is ignored too when the project's env file happens to name it, and Kerstel falls back to its default. Take the line out of that file, or run from elsewhere. Matching on the value instead would look kinder but cannot be done safely — it would mean reproducing exactly what Bun's loader puts in the environment, including $VAR expansion and escape decoding, and every difference between the two would be a way to slip a setting past the check. The resolver daemon is started in ~/.kerstel rather than your project or your home directory, so no env file reaches it at all.

Exit codes

Commands exit 0 on success and non-zero on any failure. Errors go to stderr and name the fix, usually kerstel doctor. Plaintext values never appear in error output.

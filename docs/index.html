Kerstel

Local-first secrets for Node and Bun projects. Your .env holds references. The values never touch disk in the clear.

.env
# safe to read, grep, and commit
OPENAI_API_KEY=ks:global
$ curl -fsSL https://kerstel.dev/install.sh | bash

macOS and Linux. Installs kerstel and its shorthand, ks. No account, no cloud, no telemetry.

The problem

Plaintext .env files leak

Anything that can read files can read your secrets: AI coding agents, editor plugins, backup tools, and the commit you did not mean to make. Other tools fix this with a cloud account and a wrapper command you type on every run. Kerstel needs no account, and writes its wrapper into your scripts once, so npm run dev is still npm run dev.

Demo

The whole flow in 37 seconds

A plaintext key becomes a reference, kerstel init migrates the project, and the same wiring runs under npm, Bun, pnpm, and Yarn.

How it works

Store once. Reference everywhere.

Run ks set global/OPENAI_API_KEY once (ks is short for kerstel). From then on your project file holds OPENAI_API_KEY=ks:global and your code still reads the real value from process.env. ks init does the whole project at once, and wires your scripts for you.

Vault

Values are encrypted at rest with AES-256-GCM. The data key lives in your OS credential store, or in a 0600 file where there is none.

Daemon

A per-user resolver unlocks the vault once and answers lookups over a local socket. Nothing leaves your machine.

Hook

A small preload intercepts reads of process.env and swaps each reference for its value. The file on disk never changes.

AI agents

Let your agent set it up, without seeing a value

Paste this into Claude Code, Cursor, Codex, or any agent that runs commands in your project. It works only through Kerstel's own commands, which mask every value, and it asks you before it changes your project.

Prompt for your agent
Set up Kerstel (https://kerstel.dev) in this project, so its .env files hold references and the secret values live in Kerstel's encrypted vault.

Rules for this whole task:
- Never open, print, grep or copy the contents of an .env file, and never run `kerstel get --reveal`. The kerstel commands below show key names and mask every value. Use them to see what is there.
- Never put a secret value in a command. If a step needs one, ask me to run `kerstel set <scope>/<KEY>` in my own terminal.
- Don't commit or push anything.

Steps:
1. Run `kerstel --version`. If Kerstel isn't installed, run `curl -fsSL https://kerstel.dev/install.sh | bash`. If the installer says ~/.local/bin is not on PATH, call it as ~/.local/bin/kerstel for the rest of this task.
2. Run `kerstel scan . --keys`. It lists each env file and the keys it holds in plain text, by line number, never a value. It exits 1 when it finds a secret. That is expected.
3. From the project root (the folder with package.json, or the workspace root of a monorepo), run `kerstel init --dry-run --yes`. It prints the plan and every diff with values masked, and writes nothing.
4. Summarise the plan for me: which keys go to this project's vault, which go to the vault shared by all my projects (global), which stay in plain text, and which package.json scripts get wired. Then stop and ask me to approve it. If I want a key somewhere else, tell me to run `kerstel init` in my own terminal instead, where it asks me about each one.
5. Once I approve, run `kerstel init --yes`. It backs up the original files, encrypted, before it writes. On macOS the first run may show a Keychain dialog for me to allow.
6. Run `kerstel doctor` and follow any "Fix:" line it prints. Then run `kerstel scan .` again to confirm no secret is left in plain text.
7. Tell me which files to commit: the rewritten env files, package.json and .kerstel/exec.cjs. If .gitignore still hides the env files, say so: `kerstel init --yes` leaves .gitignore as it is.
Security model

Clear about what is protected

  • No plaintext secret ever sits in a project file. Reading, grepping, or committing .env yields only references.
  • Each value is encrypted with its own random nonce. The key that unlocks them is held by the macOS Keychain or Linux's Secret Service.
  • Code that runs inside your project can still read resolved values. That is the boundary Kerstel draws today, and per-process approval is the next step.
